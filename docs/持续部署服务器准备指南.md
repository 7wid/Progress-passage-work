# 持续部署：服务器准备与首次切换指南

本文只负责从“镜像已成功发布到 GHCR”推进到“服务器具备安全部署能力”。第一次切换仍由维护人员在服务器上手动执行并观察；确认可靠后，再接入 GitHub Actions 自动触发。

## 1. 这套方案会做什么

- 生产服务器不再编译源码，只拉取 CI 发布的、带完整 Git SHA 的前后端镜像。
- 每次只更新 `backend` 与 `frontend`，不重建 `mysql`，不运行 `docker compose down`。
- 继续使用已核实的业务数据目录：
  - `/data/volumes/tech-request-prod/mysql`
  - `/data/volumes/tech-request-prod/uploads`
  - `/data/volumes/tech-request-prod/logs`
  - `/data/volumes/tech-request-prod/backups`
- 更新前先生成数据库压缩备份；健康检查失败时恢复上一版应用镜像。
- 不删除旧镜像、旧备份、旧源码目录或历史命名卷。清理工作必须另行评估。

> 重要：应用镜像可以自动恢复，但 Flyway 已执行的数据库迁移不会自动反向执行。以后新增迁移必须遵守“向后兼容”原则，例如先新增字段、后续版本再删除旧字段。

| ------------------------------------------------------- | ----------------------------------- | -------------------- |

## 3. 合并本分支之前

1. 在本地查看本分支的文件差异。
2. 确认 CI 的 `Configuration / validate`、后端测试和前端质量检查全部通过。
3. 由你完成 Git 提交、推送和 Pull Request；本指南不会替你提交。
4. Pull Request 合并到 `main` 后，等待 `Publish container images` 成功，记下该次 `main` 的完整 40 位提交 SHA。

不要直接把当前服务器的 `.env.prod`、`maven-settings.xml`、SSH 私钥或任何密码复制进仓库、聊天或截图。

## 4. 第一次服务器操作前的停止条件

以下任一条件不满足，就停止，不执行切换：

- `https://job.gxutech.xyz/` 和健康检查当前正常；
- `/var/lib/containerd` 所在分区至少有 5 GiB 可用空间；
- `/data/volumes/tech-request-prod/backups` 所在分区至少有 5 GiB 可用空间；
- 四个业务数据目录（mysql、uploads、logs、backups）均存在；
- 已确认当前三个容器属于 `tech-request-prod`；
- `/home/Ted_Kasane/progress-passage-work` 的未提交改动保持原样；
- GHCR 中同一个 SHA 的前后端镜像都存在且服务器能够拉取；
- 有维护窗口，且有人能在失败时继续处理。

## 5. 服务器目录布局

服务器管理员应建立独立目录，不在旧源码工作树中继续修改：

```text
/home/Ted_Kasane/tech-request-prod-deploy/
├── docker-compose.yml
├── deploy.sh
├── .env.prod
├── release.env
├── deploy.lock
└── history/

/data/volumes/tech-request-prod/
├── mysql/
├── uploads/
├── logs/
└── backups/
    └── mysql-时间戳.sql.gz
```

要求：

- 目录及文件只授权给该项目的部署账号；不要对 `/data`、`/home` 做递归 `chown` 或 `chmod`。
- `.env.prod` 权限必须是 `600`。
- `history` 与 `/data/volumes/tech-request-prod/backups` 必须存在，并且部署账号可写。
- `deploy.sh` 需要可执行权限；不要给它设置 SUID。

本服务器使用 Docker 29 的 containerd snapshotter。虽然 Docker `data-root` 是 `/home/docker`，镜像内容和容器快照仍位于 `/var/lib/containerd`，因此部署脚本会在拉镜像前单独检查该分区的空间。不要手工删除 `/var/lib/containerd` 中的任何文件。

## 6. 首次切换为什么不能直接自动化

当前正在运行的容器由旧源码目录中的 Compose 清单创建，而新清单放在 `/home/Ted_Kasane/tech-request-prod-deploy`。两者使用相同的项目名 `tech-request-prod`，但首次接管必须人工核对最终配置、绑定目录、端口和容器差异。确认无误后，才允许新清单重建前后端。

首次切换前，`release.env` 应先记录当前容器实际使用的本地镜像，例如：

```dotenv
BACKEND_IMAGE=tech-request-prod-backend
FRONTEND_IMAGE=tech-request-prod-frontend
```

这一步的目的，是给第一次候选版本保留可恢复的上一版镜像。不要猜镜像名，应以服务器 `docker inspect` 的实际输出为准。

## 7. `deploy.sh` 的固定执行顺序

脚本接收一个完整的 40 位 `main` 提交 SHA，并依次执行：

1. 检查文件、权限、备份分区、containerd 镜像存储分区、剩余空间和 SHA 格式；
2. 使用文件锁防止两个部署同时运行；
3. 只校验 Compose，不输出展开后的机密值；
4. 只拉取前后端候选镜像，此时不启动容器；
5. 从正在运行的 MySQL 生成压缩逻辑备份；
6. 保存上一版 `release.env`；
7. 使用 `--no-deps` 只更新后端和前端，并等待健康检查；
8. 失败时恢复上一版前后端镜像；成功时输出两个应用容器状态。

脚本不会执行：

- `docker compose down`；
- `docker system prune`、`docker image prune` 或删除卷；
- 重建、停止或升级 MySQL；
- 修改其他 Compose 项目；
- 删除历史备份。

## 8. 首次人工验证项目

第一次切换后，按顺序检查：

1. `tech-request-prod-mysql-1` 的容器 ID 与启动时间没有变化；
2. 后端和前端状态均为 `healthy`；
3. 服务器本机的 `http://127.0.0.1:10080/actuator/health` 返回成功；
4. 公网首页、登录、需求列表、需求提交和附件上传下载正常；
5. OpenResty/Nginx 代理没有 502、504；
6. `/data/volumes/tech-request-prod/backups` 中出现非空的 `.sql.gz`；
7. 观察应用日志至少 10 分钟，没有持续数据库、Flyway、权限或磁盘错误。

验证失败时不要运行 `compose down`，也不要清理镜像或卷。保留终端输出和容器日志，再按故障点处理。

## 9. 后续才接入 GitHub Actions

只有首次人工部署完成且以上检查全部通过后，才进行下一阶段：创建受限部署 SSH 密钥、把服务器主机指纹和连接信息放入 GitHub `production` Environment，并增加部署工作流。部署工作流只能调用服务器上的 `deploy.sh <SHA>`，不能获得任意 root 权限。

这样把风险分成两步：先证明服务器部署脚本可靠，再让 GitHub 自动调用它。
