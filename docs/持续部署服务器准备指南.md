# 持续部署：服务器准备与首次切换

> 更新：2026-09-12。面向现有 Linux 服务器的 GHCR 拉取式部署。本文描述仓库配置，不能证明服务器当前已经安装或开启自动部署。

## 1. 先选对部署方式

| 入口                             | 用途                       | 数据方式                                   |
| -------------------------------- | -------------------------- | ------------------------------------------ |
| 根 docker-compose.yml            | 本地开发 MySQL             | tech-request-dev 命名卷                    |
| 根 docker-compose.prod.yml       | 新环境从源码构建完整生产栈 | tech-request-prod 命名卷                   |
| deploy/server/docker-compose.yml | 已有服务器拉取成对应用镜像 | /data/volumes/tech-request-prod 下绑定目录 |

新建源码环境见[源码构建部署与运维](源码构建部署与运维.md)。已有服务器不能通过执行另一套 Compose 初始化命令直接迁移。

当前自动链路为 main push CI 成功 → 发布应用镜像 → 发布 GHCR production 记录 → 服务器定时拉取与校验 → 备份、更新前后端并验收。GitHub 不通过 SSH 调用服务器；不需要按旧教程新增 SSH Secrets 或向 CI 追加部署 job。

## 2. 仓库与服务器边界

| 项目         | 事实来源/作用                                                                                            |
| ------------ | -------------------------------------------------------------------------------------------------------- |
| CI           | [.github/workflows/ci.yml](../.github/workflows/ci.yml)，质量及部署配置检查                              |
| 发布端       | [.github/workflows/publish-images.yml](../.github/workflows/publish-images.yml)，应用与 release 记录镜像 |
| 部署控制文件 | [deploy/server](../deploy/server/)，脚本、Compose 和 systemd 模板                                        |
| 部署账号     | 当前脚本固定要求 Ted_Kasane；管理员负责受控安装                                                          |
| 部署目录     | /home/Ted_Kasane/tech-request-prod-deploy                                                                |
| 业务数据     | /data/volumes/tech-request-prod/{mysql,uploads,logs,backups}                                             |
| 入口         | 当前项目文档使用 https://job.gxutech.xyz；本机验收端口以实际 HTTP_PORT 为准，现有示例为 10080            |

这些路径、账号和平台约束来自项目实现；换服务器需先审查代码常量、Compose 和单元配置，不是仅替换本文示例。

## 3. 第一次接管前核对

- 确認当前网站及健康检查正常，记录三个现有容器的项目名、ID、镜像引用与实际挂载。
- 独立部署目录已有 .env.prod、release.env 和 history；生产秘密不进入仓库，不打印展开的 Compose 配置。
- 四个业务数据目录存在且授权正确；备份分区与 /var/lib/containerd 所在分区均至少有 5 GiB 可用空间。脚本固定检查后者，不能只看 Docker data-root。
- 同一次批准发布的前后端镜像可从 GHCR 读取，平台满足脚本要求的 linux/amd64。
- 数据库与附件已有可恢复的、时间对应的备份，迁移兼容性与维护窗口明确。
- 保留服务器旧源码工作区、既有配置、业务数据和旧应用镜像；先确认现有 systemd 安装与状态，不重复初始化。

```text
/home/Ted_Kasane/tech-request-prod-deploy/
  docker-compose.yml  deploy.sh  pull-agent.py
  notify-failure.py   retention.py
  .env.prod          release.env
  history/           deploy.lock
  pull-agent-state.json  pull-agent.lock
/data/volumes/tech-request-prod/
  mysql/ uploads/ logs/ backups/
```

初始 release.env 必须反映当前运行镜像，不能猜名字或直接填候选版本。对已部署服务器的控制文件升级，先备份，再核对同一批准提交的文件及 SHA256；保留秘密、状态和锁文件。

## 4. 分阶段执行

| 阶段       | 操作与完成条件                                       | 详细步骤                                  |
| ---------- | ---------------------------------------------------- | ----------------------------------------- |
| 发布端     | CI 成功、两个镜像和发布记录来自同次运行，权限可读    | [GHCR 发布说明](CD-pull-ghcr.md)          |
| 服务器安装 | 核对脚本、Compose、单元、所有者、权限和目录          | [拉取端 A](CD-pull-agent.md)              |
| 预检       | 单次 dry-run，检查记录和平台，不更新应用             | [拉取端 B](CD-pull-agent.md)              |
| 基线       | 使用已核对记录 digest 初始化，仅一次                 | [拉取端 C](CD-pull-agent.md)              |
| 单次部署   | 独立 enabled 开关和 apply 模式，备份后更新应用并验收 | [拉取端 D](CD-pull-agent.md)              |
| 告警与容量 | 安装 credential，确认邮件送达，先 dry-run 保留任务   | [告警与保留](CD-email-alert-retention.md) |
| 周期运行   | 单次部署和恢复验证通过后启用 timer                   | [拉取端 E](CD-pull-agent.md)              |

默认 service 是 dry-run，安装代码不会自动部署。手动运行 Publish container images 不更新 production 记录。每一步保存环境与执行结果，不将整篇文档拼成一个脚本执行。

## 5. 部署脚本与数据保护

deploy.sh 支持旧的完整提交 SHA 接口，以及拉取端使用的 `--digests COMMIT BACKEND_AT_DIGEST FRONTEND_AT_DIGEST CURRENT_RELEASE_ENV_SHA256` 接口。自动路径始终用校验后的成对 digest，不能把可变 sha 标签当作固定内容。

脚本取得共用部署锁，核对配置与磁盘，拉取应用，生成并校验 gzip 数据库备份，保存旧 release.env，仅使用 --no-deps 更新前后端并检查健康；失败时尝试恢复上一版应用。它不重建 MySQL，不自动回退 Flyway，也不自动备份附件。

retention.py 是独立程序，具备自己的开关；部署脚本本身不删除历史备份。数据库和附件的异机副本、恢复演练由运维维护。

## 6. 首次验收与日常维护

部署后检查 MySQL ID 未变，前后端健康，数据库备份非空可解压，本机及外网健康正常；使用专用账号验证登录、需求列表/提交、附件和本次变更。记录当前引用、发布记录摘要和观察结果。

配置变更需重新创建后端，restart 不更新环境。拉取代理会检查容器基线；人工操作前先停 timer 并等待正在执行的 service 完成，操作后按[状态协调与恢复](CD-pull-agent.md)核对，不清空状态重新初始化。

故障先停后续调度、保存日志并检查状态，应用回退成功仍需确认数据库兼容性。不要执行 down -v、全局 prune、删除状态/锁或覆盖数据目录。邮箱找回 SMTP 与 CD 告警 credential 属于两套独立配置，分别验收。
